The homepage is findable and its layout is already stable, but the first screen is slow. WP-Optimize is already caching and minifying, so the delay is not “no cache plugin”. It is HTTP/1.1 plus a long queue of render-blocking CSS, JavaScript and icon fonts.

Google PageSpeed Insights was not measured on this run (the public API returned HTTP 429). Figures below are from Lighthouse 13.6.0 on this machine, plus our own HTTP fetches. No numbers were invented.

Render-blocking, HTTP and headers

Render-blockingLighthouse reported 53 render-blocking CSS and JavaScript files on mobile (estimated 4,780 ms delay) and 52 on desktop (estimated 1,610 ms). Forty script tags in the HTML have no async or defer, including jQuery, GSAP, DOMPurify, Font Awesome v4 shims, theme jQuery, Bootstrap, Owl Carousel and AOS. A first pass of our scan tool missed this, because Lighthouse 13 renamed the audit; the figures here are from render-blocking-insight in the lab JSON.
HTTP versionThe host negotiated HTTP/1.1 only. TLS 1.3 is on, but ALPN selected http/1.1. Lighthouse estimated 2,640 ms savings on mobile and 2,090 ms on desktop if HTTP/2 or HTTP/3 were used. This matters because the page makes more than 130 requests.
CompressionGzip is on. A request that offered Brotli, gzip and deflate was served gzip. The 571,131-byte HTML compressed to 79,160 bytes.
CachingThe HTML response is already a WP-Optimize page cache hit (WPO-Cache-Status: cached), but its header is Cache-Control: no-cache. Static CSS, minify files and the theme woff2 font send Cache-Control: public, max-age=2592000 (30 days).
ServerApache, PHP 8.1.34, header X-WS-Origin: available.

Top 3 fixes

Plain recommendations from this scan only. Not a full recipe, and not “install a caching plugin” — WP-Optimize is already doing that.

  1. Ask the host to enable HTTP/2 or HTTP/3, and get the first paint off that long render-blocking queue. The site still answers on HTTP/1.1, then has to fetch 50-plus CSS and JavaScript files before the heading and first paragraph can paint. That is why LCP is a text element waiting, not a heavy hero image. Combine or defer what is not needed for the first screen, and inline a small amount of critical CSS. Lighthouse estimated 4.8 s of render-blocking delay on mobile and 1.6 s on desktop, plus a further 2.1–2.6 s if the host moved off HTTP/1.1.
  2. Load Font Awesome once, and only the icons in use. The theme, Elementor, Font Awesome Pro and Font Awesome 5 are all shipping icon CSS or webfonts. Together, fonts were about 619 KiB on the mobile lab run, and the single heaviest file was a 725 KiB minified Font Awesome footer script. About 99% of the Pro CSS was unused. One icon method, subset to the icons on the site, would cut a large share of the weight without changing the look.
  3. Cut first-load JavaScript without touching reviews, forms or the layout. The theme loads a second copy of jQuery. Happy Elementor Addons pulls in GSAP on the homepage. Elementor’s Swiper was almost unused. Google Tag Manager is 183 KiB on first load. Trustindex can be deferred so the Google reviews still appear, just not on the critical path. That is the practical way to bring the 952 ms mobile Total Blocking Time down. No paid plugin would be added without approval, and a full backup would be taken first.

This is a short public scan of the homepage, made from the outside. It is not a complete fix list, and it does not change the live site. Client-supplied PageSpeed attachments were not available to us when this was written.
